# Change the database schema

**When:** you add, change or drop a table, column or index; or a pulled commit changed `sql/schema.sql`,
`sql/procedures`, `sql/triggers`, `sql/events` or `sql/seed`. There are no migration files: schema changes are run straight
against the database and `sql/schema.sql` is regenerated from it.

**Prerequisites:** a fresh backup (`backup-restore.md`); the server stopped for DDL on a table players write to
(`items`, `characters`, `vehicles`, `accounts`); procedures, triggers, events and seeds can be applied live.

## How the files relate

- `sql/schema.sql` is the current schema: one `CREATE TABLE IF NOT EXISTS` per table, generated by
  `python -m tools.sqltool --db scavengesurvive dump`. Never edit it by hand.
- `python -m tools.sqltool --db NAME apply` runs `schema.sql` (creates only the tables that are missing; an existing
  table is never altered), then procedures, triggers and events (`CREATE OR REPLACE`) and seeds (idempotent).
  Triggers are files because `SHOW CREATE TABLE` (and so `dump`) leaves them out. `--reset` drops
  the database first. `run-local.ps1` runs `apply` on every start.
- `pytest -q tests/sql` rebuilds `scavengesurvive_test` from scratch (`apply --reset`), so the test database follows
  `schema.sql` without being altered by hand.

## Steps (schema change)

1. Write the DDL (`ALTER TABLE … ADD COLUMN …`, `CREATE TABLE …`). DDL on a system-versioned table (`accounts`,
   `items`, `bans`) runs `SET SESSION system_versioning_alter_history = KEEP;` first in the same session, or MariaDB
   refuses it (error 4119).
2. Run it against the live database:
   `mariadb -u root scavengesurvive -e "SET SESSION system_versioning_alter_history = KEEP; ALTER TABLE …"`.
3. Regenerate the schema: `python -m tools.sqltool --db scavengesurvive dump`, then `git diff sql/schema.sql` must
   show only the change you made.
4. Test: `python -m pytest -q tests/sql` (recreates `scavengesurvive_test` from the new `schema.sql`).
5. Restart the resources that read the changed tables (`rr items`, `rr staff`, …) or do a full start.
6. Commit the regenerated `sql/schema.sql` with the code that uses it; put the DDL in the commit body, because
   `apply` will not add a column to a table that already exists on another database.

One-off data fixes (remapping values, repairing rows) run directly with `mariadb`, after a backup, with no file.

## Steps (pulled changes, another database)

1. Procedures, triggers, events and seeds: `python -m tools.sqltool --db scavengesurvive apply` (add `--password` when
   needed). Running it twice is safe.
2. New tables arrive with the same `apply`. A changed existing table does not: run the DDL from the commit that
   changed `schema.sql`. To see what this database lacks, `dump` it and `git diff sql/schema.sql` (then
   `git restore sql/schema.sql`); the diff is the difference between this database and the commit.
3. Verify: `SHOW EVENTS` lists `ev_despawn_items` and `ev_expire_bans` with `ENABLED`; `SELECT @@event_scheduler`
   is `ON` (it is lost on a MariaDB restart unless `event_scheduler=ON` is in `my.ini`).

## Rollback

There is no down step. Run the reverse DDL (`ALTER TABLE … DROP COLUMN …`) and `dump` again, or restore the backup
taken in the prerequisites (`backup-restore.md`). Seeds never delete rows, so a wrong seed value is corrected by the
next seed run (`svalue = svalue` keeps edited settings; change the key if the default must win).

## Escalation

Whoever made the change; the repository owner for anything touching `accounts` or `items` history.
