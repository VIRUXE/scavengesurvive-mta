# Change the database schema

**When:** you add, change or drop a table, column, index, procedure, function, trigger or event; or a pulled commit
changed `sql/schema.sql` or `sql/seed`. There are no migration or procedure files: every change is run straight
against the database and `sql/schema.sql` is regenerated from it.

**Prerequisites:** a fresh backup (`backup-restore.md`); the server stopped for DDL on a table players write to
(`items`, `characters`, `vehicles`, `accounts`); procedures, triggers, events and seeds can be changed live.

## How the files relate

- `sql/schema.sql` is the current database: one `CREATE TABLE IF NOT EXISTS` per table, then a `DELIMITER //` block
  with every procedure, function, trigger and event as `CREATE OR REPLACE`, generated by
  `python -m tools.sqltool --db scavengesurvive dump` (`SHOW CREATE TABLE/PROCEDURE/FUNCTION/TRIGGER/EVENT`). Never
  edit it by hand.
- `python -m tools.sqltool --db NAME apply` runs `schema.sql` (creates only the tables that are missing, an existing
  table is never altered; replaces every routine, trigger and event), then the seeds (idempotent). `--reset` drops
  the database first. `mariadb NAME < sql/schema.sql` does the same as the first half, since it honours `DELIMITER`.
  `run-local.ps1` runs `apply` on every start.

## Steps (table change)

1. Write the DDL (`ALTER TABLE … ADD COLUMN …`, `CREATE TABLE …`). DDL on a system-versioned table (`accounts`,
   `items`, `bans`) runs `SET SESSION system_versioning_alter_history = KEEP;` first in the same session, or MariaDB
   refuses it (error 4119).
2. Run it against the live database:
   `mariadb -u root scavengesurvive -e "SET SESSION system_versioning_alter_history = KEEP; ALTER TABLE …"`.
3. Regenerate the schema: `python -m tools.sqltool --db scavengesurvive dump`, then `git diff sql/schema.sql` must
   show only the change you made.
4. Verify on the live server (no automated tests).
5. Restart the resources that read the changed tables (`rr items`, `rr staff`, …) or do a full start.
6. Commit the regenerated `sql/schema.sql` with the code that uses it; put the DDL in the commit body, because
   `apply` will not add a column to a table that already exists on another database.

## Steps (procedure, function, trigger or event)

1. Write it as `CREATE OR REPLACE PROCEDURE …` (or `FUNCTION`, `TRIGGER`, `EVENT`) and run it against the live
   `scavengesurvive` database, e.g. from a scratch file with `mariadb -u root scavengesurvive < scratch.sql` (wrap the
   body in `DELIMITER //` … `//`). Keep the scratch file out of the repository. Dropping one is `DROP … IF EXISTS`.
2. `python -m tools.sqltool --db scavengesurvive dump`; `git diff sql/schema.sql` must show only that routine.
3. Commit the regenerated `sql/schema.sql`. No resource restart is
   needed: the next `CALL` uses the new body.

One-off data fixes (remapping values, repairing rows) run directly with `mariadb`, after a backup, with no file.

## Steps (pulled changes, another database)

1. Procedures, functions, triggers, events, new tables and seeds: `python -m tools.sqltool --db scavengesurvive apply`
   (add `--password` when needed). Running it twice is safe. A routine dropped upstream is not dropped here; run the
   `DROP` by hand.
2. A changed existing table does not arrive with `apply`: run the DDL from the commit that changed `schema.sql`. To
   see what this database lacks, `dump` it and `git diff sql/schema.sql` (then `git restore sql/schema.sql`); the
   diff is the difference between this database and the commit.
3. Verify: `SHOW EVENTS` lists `ev_despawn_items` and `ev_expire_bans` with `ENABLED`; `SELECT @@event_scheduler`
   is `ON` (it is lost on a MariaDB restart unless `event_scheduler=ON` is in `my.ini`).

## Rollback

There is no down step. Run the reverse DDL (`ALTER TABLE … DROP COLUMN …`) and `dump` again, or restore the backup
taken in the prerequisites (`backup-restore.md`). Seeds never delete rows, so a wrong seed value is corrected by the
next seed run (`svalue = svalue` keeps edited settings; change the key if the default must win).

## Escalation

Whoever made the change; the repository owner for anything touching `accounts` or `items` history.
